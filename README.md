# Edelya

Edelya — backend-сервис для приложения по ведению рецептов, планированию питания, формированию списков покупок и управлению платным доступом. Проект построен на Django, Django REST Framework и Celery, ориентирован на Telegram Mini App/Web App сценарий и использует подписочную модель доступа.

## Возможности от 16.06.2026

### Аутентификация и доступ

- JWT-аутентификация через `djangorestframework-simplejwt`.
- Получение пары access/refresh токенов по логину и паролю.
- Получение JWT через Telegram Web App init data:
  - проверка подписи Telegram-данных;
  - создание пользователя по `telegram_id`, если он заходит впервые;
  - сохранение Telegram-профиля пользователя;
  - требование пользовательских согласий при первой регистрации.
- Обновление access-токена через refresh-токен.
- Глобальная проверка подписки при доступе к защищенным API:
  - отсутствие подписки;
  - истекший trial;
  - истекшая активная подписка;
  - `PAST_DUE` вне grace period;
  - отмененная или истекшая подписка.
- Разделение прав по возможностям тарифа:
  - доступ к базовым функциям;
  - доступ к созданию AI-рецептов;
  - проверка активного trial.
- Проверка владения объектами: пользователь работает только со своими блюдами, ингредиентами, планами, списками покупок и подпиской.

### Пользователи, согласия и юридические документы

- Кастомная модель пользователя с Telegram-полями:
  - `telegram_id`;
  - имя и username из Telegram;
  - статус активности Telegram-канала;
  - JSON-данные онбординга;
  - флаг согласия на маркетинговые коммуникации.
- Получение и обновление данных онбординга текущего пользователя.
- Хранение журналов согласий:
  - пользовательское соглашение;
  - политика конфиденциальности;
  - маркетинговые коммуникации;
  - согласие на сохранение платежного метода;
  - IP-адрес, user-agent и версии документов на момент согласия.
- Версионирование юридических документов:
  - Terms of Service;
  - Privacy Policy;
  - список опубликованных версий;
  - получение актуальной версии документа.

### Ингредиенты

- Справочник категорий ингредиентов.
- Пользовательские и системные ингредиенты:
  - системные ингредиенты доступны всем пользователям;
  - пользовательские ингредиенты доступны только владельцу.
- Базовые единицы измерения ингредиентов.
- Нормализация названий перед сохранением.
- Уникальность названий отдельно для системных и пользовательских ингредиентов.
- Мягкое удаление пользовательских ингредиентов через деактивацию.
- Фильтрация и поиск ингредиентов.
- PostgreSQL trigram index для поиска похожих названий ингредиентов с нормализацией `ё`/`е`.

### Блюда и рецепты

- Справочник категорий блюд.
- Пользовательские и системные блюда.
- CRUD для блюд пользователя.
- У блюда хранится:
  - категория;
  - название;
  - текст рецепта;
  - набор ингредиентов;
  - количество каждого ингредиента;
  - признак опционального ингредиента;
  - позиция ингредиента в рецепте.
- Нормализация названий блюд.
- Уникальность активных блюд:
  - отдельно для системных блюд;
  - отдельно внутри пользователя.
- Мягкое удаление блюда:
  - блюдо деактивируется;
  - связи с ингредиентами удаляются.
- При создании и обновлении блюда используется сервисная логика, которая синхронизирует состав ингредиентов.
- Отдельные read/write сериализаторы: API возвращает расширенные данные, а запись принимает структуру для создания/обновления.

### AI-черновики рецептов

- Создание AI-черновика блюда из исходного текста рецепта.
- Фоновая обработка черновиков через Celery.
- Интеграция с OpenAI для разбора рецепта в структурированный payload.
- Статусы AI-черновика:
  - обработка;
  - успешно разобран;
  - ошибка обработки;
  - блюдо создано из черновика.
- Сохранение:
  - исходного текста;
  - сырого ответа AI;
  - OpenAI usage;
  - структурированного payload;
  - ошибок валидации;
  - ссылки на созданное блюдо.
- Повторные попытки обращения к AI при временных ошибках.
- Redis-lock на обработку черновика, чтобы несколько воркеров не обработали один черновик одновременно.
- Автоматическая повторная постановка зависших `PROCESSING`-черновиков в обработку.
- Подготовка payload для формы создания блюда:
  - определение категории блюда;
  - нормализация названий ингредиентов;
  - сопоставление с существующими ингредиентами пользователя;
  - поиск похожих ингредиентов;
  - автоматическое использование точного похожего ингредиента;
  - список suggested ingredient IDs для неоднозначных совпадений;
  - создание новых пользовательских ингредиентов при подтверждении payload.
- Создание полноценного блюда из разобранного AI-черновика.
- Ограничение создания AI-рецептов по тарифу и лимиту на период подписки.

### Планирование питания

- План питания строится вокруг недельного календаря.
- Получение блюд на конкретную ISO-неделю по `year` и `week`.
- Ручное добавление блюд в план на дату.
- Управление элементами плана:
  - дата;
  - блюдо;
  - позиция внутри дня;
  - цвет;
  - признак ручного добавления;
  - связь с событием готовки.
- Частичное обновление элементов плана.
- Удаление элементов плана.
- Индексы по пользователю, дате, позиции и источнику готовки для быстрых календарных выборок.

### События готовки

- Создание событий готовки для блюда на конкретную дату.
- Хранение заметок к готовке.
- Позиционирование событий внутри дня.
- Цветовая маркировка событий.
- Связь события готовки с автоматически созданными элементами плана питания.
- Обновление события готовки через сервис, который синхронизирует связанные данные плана.
- Удаление события вместе с зависимыми элементами плана.

### Списки покупок

- Создание списков покупок на период дат.
- Список содержит:
  - название;
  - владельца;
  - дату начала периода;
  - дату окончания периода;
  - позиции списка.
- Автоматический пересчет списка покупок по блюдам из плана питания за выбранный период.
- Суммирование количества одинаковых ингредиентов из разных блюд.
- Создание новых позиций списка при появлении ингредиентов в плане.
- Обновление количества существующих позиций при изменении плана или периода.
- Удаление автоматически созданных позиций, если ингредиент больше не нужен.
- Сохранение ручных позиций пользователя:
  - ручные позиции не удаляются автоматическим пересчетом;
  - если ручная позиция совпала с рассчитанным ингредиентом, она становится автоматической и получает рассчитанное количество.
- Ручной запуск пересчета через отдельное действие API.
- CRUD для позиций списка покупок:
  - ингредиент;
  - количество;
  - отметка `куплено`;
  - время отметки;
  - ручное добавление;
  - позиция сортировки.
- Уникальность ингредиента внутри одного списка покупок.

### Подписки и тарифы

- Публикуемые тарифы с сортировкой.
- Настройки тарифа:
  - цена;
  - период оплаты: месяц или год;
  - описание и пункты описания;
  - признак trial-тарифа;
  - длительность trial;
  - статус публикации;
  - статус активности;
  - признак `скоро будет`;
  - доступ к базовым функциям;
  - доступ к AI-рецептам;
  - возможность общего пространства.
- Только один активный trial-тариф.
- Получение списка тарифов.
- Получение длительности trial.
- Получение словаря подписочной модели:
  - длительность trial по умолчанию;
  - длительность grace period;
  - лимит AI-рецептов на период.
- Старт trial-подписки.
- Получение текущей подписки пользователя.
- Получение использования AI-рецептов за период подписки.
- Выбор тарифа с учетом текущего состояния подписки:
  - в trial без карты запускается привязка карты через YooKassa;
  - в trial с картой тариф планируется как `pending_tariff`;
  - для истекшей или отмененной подписки создается первый платеж;
  - для активной подписки поддерживается смена тарифа.
- Upgrade активного тарифа:
  - расчет пропорциональной доплаты за остаток периода;
  - списание через сохраненный платежный метод;
  - немедленная смена тарифа при успешном сценарии.
- Downgrade активного тарифа:
  - планирование смены тарифа на следующий billing cycle;
  - уведомление пользователя о запланированной смене.
- Отмена подписки:
  - отключение автопродления;
  - сохранение даты отмены.
- Возобновление подписки.
- Повторная попытка оплаты для проблемной подписки.
- Grace period для `PAST_DUE` подписок.
- Автоматическое истечение trial, отмененных и просроченных подписок.

### Платежи и платежные методы

- Интеграция с YooKassa.
- Создание платежей:

  - платеж за upgrade;
  - повторная попытка платежа;
  - нулевая привязка карты.
- Сохранение платежей в БД:

  - сумма и валюта;
  - статус;
  - тип платежа;
  - idempotence key;
  - дата оплаты;
  - причина отмены;
  - metadata;
  - связанный платежный метод.
- Привязка карты через YooKassa confirmation URL.
- Получение текущего платежного метода пользователя.
- Удаление платежного метода.
- Хранение данных карты для отображения:
  - тип платежного метода;
  - последние 4 цифры;
  - тип карты;
  - название метода;
  - активность.
- Обработка webhook YooKassa:
  - `payment.succeeded`;
  - `payment.canceled`;
  - `payment_method.active`.
- Идемпотентная обработка уже успешных или отмененных платежей.
- Обновление подписки после успешного первого или рекуррентного платежа.
- Сохранение/обновление платежного метода после успешного платежа или активной привязки.
- Уведомления пользователю по результатам платежных событий.

### Фискальные чеки Tax3r

- Интеграция с Tax3r для отправки чеков.

- Отправка пользователю уведомления со ссылкой на чек.

### Фоновые задачи

Проект использует Celery и `django-celery-beat`. Периодические задачи создаются идемпотентно через сервис настройки расписания.

- Каждые 5 минут:
  - конвертация trial в платную подписку перед окончанием trial;
  - автопродление активных подписок;
  - повторное списание для `PAST_DUE` подписок.
- Каждые 2 минуты:
  - повторная обработка зависших AI-черновиков.
- Каждые 20 секунд:
  - обработка результатов Tax3r из Redis.
- Ежедневно:
  - истечение брошенных trial без выбранного тарифа;
  - истечение `PAST_DUE` после grace period;
  - истечение отмененных подписок после конца оплаченного периода;
  - истечение брошенных нулевых привязок карты.

### API и документация

- REST API версии `v1` доступен под `/api/v1/`.
- OpenAPI-схема доступна под `/api/schema/`.
- Swagger UI доступен под `/api/docs/`.
- Healthcheck endpoint: `/ping/`.
- Основные группы API:
  - `/api/v1/auth/` — JWT и Telegram-аутентификация;
  - `/api/v1/users/me/onboarding-data/` — данные онбординга;
  - `/api/v1/legal/terms-of-service/` — версии пользовательского соглашения;
  - `/api/v1/legal/privacy-policy/` — версии политики конфиденциальности;
  - `/api/v1/ingredient-categories/` — категории ингредиентов;
  - `/api/v1/ingredients/` — ингредиенты;
  - `/api/v1/dish-categories/` — категории блюд;
  - `/api/v1/dishes/` — блюда и рецепты;
  - `/api/v1/ai-drafts/` — AI-черновики рецептов;
  - `/api/v1/planning/year/<year>/week/<week>/` — недельный план;
  - `/api/v1/planning/cooking-events/` — события готовки;
  - `/api/v1/planning/meal-plan-items/` — элементы плана питания;
  - `/api/v1/shopping/shopping-lists/` — списки покупок;
  - `/api/v1/shopping/shopping-lists/<shopping_list_id>/items/` — позиции списка покупок;
  - `/api/v1/subscriptions/` — подписка текущего пользователя и действия с ней;
  - `/api/v1/subscriptions/tariffs/` — тарифы;
  - `/api/v1/subscriptions/payment-method/` — платежный метод пользователя;
  - `/api/v1/subscriptions/webhooks/yookassa/` — webhook YooKassa.

## Переменные окружения

Проект читает настройки из окружения и `.env`.

- `SECRET_KEY` — секрет Django.
- `DEBUG` — режим отладки, `0` или `1`.
- `ALLOWED_HOSTS` — список host'ов через `, `.
- `CORS_ALLOWED_ORIGINS` — разрешенные origins через `, `.
- `CSRF_TRUSTED_ORIGINS` — trusted origins через `, `.
- `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` — подключение к PostgreSQL.
- `REDIS_URL` — базовый Redis URL.
- `CLUSTER_REDIS_URL` — Redis для кластерных/очередных операций.
- `EDELYA_BOT_TOKEN` — токен Telegram-бота.
- `FRONTEND_URL` — URL фронтенда для возврата после платежа.
- `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` — YooKassa.
- `TAX3R_URL`, `TAX3R_API_KEY`, `SEND_CHECKS_TO_TAX3R` — Tax3r.
- `SERVICE_NAME` — имя сервиса, используется в очередях и логировании.
- `LOKI_CONTAINER`, `LOKI_APP_NAME` — настройки Loki.
